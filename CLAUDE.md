# jobforge

## Purpose and motivation
jobforge is a small multi-tenant job scheduler with per-tenant rate limiting. It is a portfolio project built to practice, at small scale, the design problems that large cloud platforms solve:
- durable scheduling (recurring and one-off jobs that must not be lost),
- workers that can crash at any time without losing or doubling work,
- retries and dead-lettering,
- fairness between tenants sharing the same workers,
- quota-based API rate limiting.
The owner is a final-year student targeting SDE roles. The project exists so she can explain a real distributed-systems design in interviews, with her own measured results. Understanding matters more than speed or feature count. She must be able to explain every line.

## What the system does
A tenant (a customer account) defines jobs through an HTTP API. A job is either one-off or recurring (interval_seconds). The scheduler turns a job into runs: one run is one scheduled occurrence of a job. Workers claim runs, execute them, and record the outcome. If a worker dies mid-run, the run is recovered and executed again by another worker. If a run keeps failing, it moves to a dead-letter table and can be redriven explicitly. The API limits how much each tenant can submit, so one noisy tenant cannot starve the others.

## Architecture
- API (FastAPI, app/main.py): tenants, jobs, run status, redrive. Rate limiting sits in front of job submission.
- Scheduler (app/scheduler.py, own process): creates runs when jobs come due. Later also hosts an SLA verifier that flags occurrences that should have run but did not.
- Workers (app/worker.py, run several copies): claim a run with a lease, execute it, heartbeat while running, then complete or fail it.
- PostgreSQL: the single source of truth for jobs, runs, attempts and dead letters. It is also the queue.
- Redis: rate limiter state only (token buckets and hourly quota counters). Nothing durable lives in Redis.
Flow: API writes a job -> scheduler inserts due runs -> workers claim runs with FOR UPDATE SKIP LOCKED -> worker executes -> worker marks the run succeeded, or schedules a retry, or dead-letters it.

## Data model (migrations/001_init.sql)
- tenants: id (uuid, generated by Postgres), name (unique), points_quota_per_hour, burst_rps, max_concurrency, created_at.
- jobs: id (uuid, generated by Postgres), tenant_id (FK, cascade), name, job_type, payload (jsonb), interval_seconds (NULL means one-off), max_attempts (default 5), retention_days, version, enabled, created_at. UNIQUE (tenant_id, name).
- job_runs: id (uuid, also the idempotency key for the job's side effects), job_id, tenant_id (denormalised for fairness queries), scheduled_for, state in (ready, leased, succeeded, retry_wait, dead), attempt, available_at (backoff lives here), lease_owner, lease_expires_at, fencing_token (bigint, bumped on every claim), last_error, created_at, finished_at. UNIQUE (job_id, scheduled_for).
- run_attempts: one row per attempt (run_id, attempt, worker_id, started_at, finished_at, outcome in succeeded/failed/lease_expired, error).
- dead_letters: run_id (PK), reason, moved_at, redriven_at.
Indexes: claimable runs by available_at (partial, ready and retry_wait), (tenant_id, state), lease_expires_at (partial, leased).
Added by migrations/002_weekend2.sql: job_runs.attempt_base (attempts used before the last redrive; attempts since = attempt - attempt_base), job_effects (run_id PK, tenant_id, created_at: the idempotent side-effect record), redrive_log (id, run_id, previous_reason, note, redriven_at), and CHECK tenants_name_not_blank on tenants.name.
IDs are never sent by the client. Postgres generates them.

## Design rules that must stay true
1. Postgres is both the store and the queue. A run is claimed in one transaction with SELECT ... FOR UPDATE SKIP LOCKED, so two workers can never claim the same run and workers never block each other.
2. Leases, not "mark as running". A claim sets state=leased, lease_owner and lease_expires_at. A worker extends the lease by heartbeating. If a worker dies, the lease expires and reap_expired_leases makes the run claimable again.
3. Fencing tokens. Every claim increments fencing_token. complete, fail and heartbeat must include "WHERE fencing_token = <my token>" and check the row count. A stalled worker whose lease expired must not overwrite the newer worker's result.
4. At-least-once delivery. Exactly-once is not possible, so a run can execute more than once. The side effect must be idempotent, using the run id as the idempotency key (for example a unique constraint on an effects table).
5. Retries use exponential backoff with jitter, written to available_at. Transient errors retry. Permanent errors or attempt >= max_attempts go to dead_letters. Redrive is an explicit, auditable action.
6. Duplicate occurrences are prevented by UNIQUE (job_id, scheduled_for) with INSERT ... ON CONFLICT DO NOTHING, so running two schedulers is safe.
7. Downtime policy (decide, document, and keep consistent): after scheduler downtime, missed occurrences are skipped, caught up, or expired. The choice and its cost go in docs/DESIGN.md.
8. Fairness (Weekend 2): respect tenants.max_concurrency and claim across tenants fairly, so one tenant with 10,000 runs does not starve the others.
9. Rate limiting (Weekend 2), modelled on Jira Cloud's published design: a Redis token bucket per tenant per endpoint for bursts, plus an hourly points quota where heavier operations cost more. The read-modify-write must run in one Redis Lua script. Responses carry X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-NearLimit, and a 429 carries Retry-After.

## Tech stack and conventions
- Python 3.12, FastAPI, Pydantic v2, psycopg 3 with psycopg_pool, plain SQL (no ORM), PostgreSQL 16, Redis, pytest, ruff, Locust, GitHub Actions.
- SQL is parameterised with %s, never string formatting. JSON columns use psycopg.types.json.Jsonb.
- Style: follow the existing endpoint pattern (with get_pool().connection() as conn, catch psycopg.errors.UniqueViolation and ForeignKeyViolation, raise HTTPException ... from None). Ruff: line length 100, rules E, F, I, B.
- Job types accepted by the API today: "noop", "sleep", "record" (writes one job_effects row keyed by run id) and "flaky" (test-only: fails while attempt <= payload.fail_times). Note: JOB_TYPE_COST in app/ratelimit.py still lists placeholder types (noop, http_call, report). Align it with the real job types when the rate limiter is built.
